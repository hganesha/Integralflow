# Production slice 1: corporate party screening and ownership (US)

Status: plan approved 2026-11-09; first build landed (see §9). Nothing in this slice is
production-qualified yet. This plan names what must be true before it can be, and what this
repository builds toward that.

Companions: [skill catalog production plan](skill-catalog-production-plan.md) (maturity ladder,
twelve pilot skills), [test context corpus](test-context-corpus.md) (heroes and answer keys),
[agent profiles](agent-profiles.md), [agent loop](agent-loop.md),
[skill catalog implementation](skill-catalog-implementation.md) (`skill.qualification.v1`).

## 1. Why a slice is a workflow, not a list of skills

Production authority is enforced per skill invocation. In production the gateway refuses a skill
below `integration_verified` and one without an approved, current `skill.qualification.v1` record
for the exact plan, policy context, jurisdiction and purpose
(`apps/capability-gateway/src/adapters/skills.ts`). A synthetic-maturity skill may read only
synthetic records. A plan that mixes qualified and unqualified skills therefore fails at its first
unqualified node.

So the unit of scope is a **plan**: a small workflow whose every skill and agent is qualified
together, under one pinned policy, ending at an authorized human decision.

## 2. Scope

| Dimension | In scope | Out of scope |
| --- | --- | --- |
| Journey | Corporate onboarding: legal-entity existence, ownership/control and UBO, sanctions and PEP screening of the customer and its related parties | Identity documents, adverse media, risk tiering, EDD, recommendation, final disposition |
| Customer | Ordinary corporate customers (companies, holding groups), including layered and circular groups | Trusts, funds, charities, banks (they remain in the KYB reference domain) |
| Jurisdiction | US policy jurisdiction (FinCEN CDD 25% beneficial-ownership threshold, OFAC 50% rule) | EU screening scope (EU list not collected) |
| Purpose | `onboarding` | review, monitoring, investigation |
| End state | Independent human review of a screening-and-ownership assessment | Customer acceptance; no transaction, filing or restriction is authorized by the slice |

## 3. Decisions (simple defaults, 2026-11-09)

The owner delegated decisions 2-5 of the scoping note to simple defaults. Each is replaceable
without changing the build.

1. **Slice.** US corporate KYB screening and ownership (owner decision).
2. **Owners and reviewers.** Roles, not people: the slice policy is owned by the
   `kyb-policy-owner` role; qualification evidence is approved by an `fc-independent-qa`
   principal who is not the registrant (enforced by the artifact registry's separation of
   duties). Named people are assigned when the roles are staffed.
3. **Held-out split.** Generated procedurally from a salt that never enters the repository
   (`CORPUS_HELDOUT_SALT`), written outside the checkout; only its manifest digest and sample
   count are recorded in evaluation reports. Without the salt the harness refuses to produce a
   held-out report, so the dev split cannot be passed off as held-out.
4. **Shadow runs.** No real case data is available to this environment. Shadow mode is defined
   as an operator procedure (§7) and is a production-qualification precondition, not something
   this repository can claim.
5. **Agent models.** `model.standard.v1` for both review agents; recorded mode offline.

## 4. Workflow

`domains/kyb-screening`, generated by `scripts/sync-kyb-screening-package.mjs` from
`domains/kyb-screening/source/workflow.json` with the shared library-package generator.

```
intake

 → acquire: registry · LEI · officers · ownership (connectors)

 → ownership.graph.build → ownership.interest.calculate
 → ownership.ubo.resolve → ownership.ubo.verify
 → ownership review loop (advisory, bounded)                  [agent.identity_ownership]
 → acquire: sanctions · PEP (connectors, every case subject)
 → screening.name.normalize → screening.sanctions.execute     [agent.screening]

```

### Agents

Every skill node runs as an agent profile (`config.agentRef`), imported from the library's
business profiles with the documented field mapping. That gives least privilege per phase
(`allowedSkills`, purposes) and attribution, and calls no model.

Two **advisory review loops** are the slice's only model use:

| Node | Profile | Tools (read connectors only) | Output |
| --- | --- | --- | --- |
| `ownership-review` | `agent.identity_ownership` | registry, officers, ownership, LEI lookups | Cited findings and gaps about unresolved ownership (ranges, cycles, unaccounted interest); `requiresHumanReview: true` |
| `screening-review` | `agent.screening` | registry, identifier lookups | A non-final disposition proposal per screening candidate, with cited corroboration; never `final` |

Both are recorded as `AGENT_DERIVED` evidence with untrusted instruction status and may write
only `LinkEvidence`. They cannot write gate results, status transitions or dispositions (the
compiler refuses protected agent writes). A loop's tools are connectors, not skills, because the
platform does not yet let a loop invoke a business skill with runtime-built input (see the
scoping note's gap 2); that work is wave 2.

### Gates

| Control | Mechanism |
| --- | --- |
| Policy authority | `decision.policy.resolve` and the pinned slice policy pack; an unresolved policy field blocks the skill (`POLICY_UNRESOLVED`) |
| Evidence completeness | Required record selectors; a missing producer yields `CONTEXT_MISSING`, never a clear |
| Human authority | `decision.human.review` is human-gated: an independent approval node, then effect release |
| Agent authority | Compiler-enforced profile bounds; protected writes refused; loop limits clamped at run time |

An OPA gate bundle for KYB is not part of wave 1: it needs the policy owner's decision tables.
Until then the human approval is the only disposition authority, which is the conservative
default.

## 6. Qualification evidence

### Skills

`tools/context-corpus` gains an evaluation harness (`context-corpus evaluate`) that runs every slice
skill through the library executor on the dev heroes and, with the salt, on a procedurally
generated held-out split, and compares the results with the answer keys:

| Skill family | Metrics |
| --- | --- |
| Screening | designated-party recall, false-hit count on clean parties, disambiguation accuracy |
| Ownership | effective-interest exact-match rate, UBO set exact-match rate, unresolved-reason recall |
| OFAC 50% | blocked-determination accuracy |
| All | control pass rate (no favorable result from missing context or policy), completion rate |

The report carries `datasetDigest`, `sampleCount`, metrics and thresholds in the shape of
`skill.qualification.v1.evidence`. Thresholds are the policy owner's; the defaults in the report
are placeholders marked as such.

### Agents

`agent.qualification.v1` (packages/contracts) binds an agent profile digest, its model profile
revision digest, tool set, plan digest and scope to evidence: proposal agreement with the answer
key, citation validity, protected-write and clearing violations (must be zero), escalation
recall, and injection-resistance results. Like skills, it is approved by an independent reviewer
through the artifact registry.

## 7. Exit bar

Engineering gates (absolute, owner thresholds aside):

1. Every control case passes; no favorable outcome from missing policy or context.
2. Held-out evaluation meets the owner's thresholds for every skill and both agents.
3. Sanctions/PEP and ownership connectors are `integration_verified` against live providers with
   entitlement and coverage attestations.
4. Slice policy approved by the policy owner; a new plan compiled against it and released.
5. Shadow run: the slice plan runs read-only beside the current process on an agreed number of
   real cases; disagreements are adjudicated and recorded.
6. Rollback rehearsal; runbook and on-call owner named.
7. Qualification records registered and approved by an independent reviewer.

### Evaluation results (synthetic; not qualification)

Dev split (9 heroes) and held-out split (3 salts × 40 generated parties, 120 parties): every
applicable check passed for all 12 skills; designated-party recall 1.0 with zero false hits;
effective-interest, UBO-set, OFAC 50% and disambiguation agreement 1.0. Every control case
(policy field absent, required records absent) produced no favorable result. A negative test shows the
harness fails when a skill's behavior changes (path-product aggregation in place of the OFAC rule).
Held-out case mix per 40 parties: 4-7 OFAC-blocked groups, 5-6 circular holdings, 5-10 ownership ranges,
17-23 with unaccounted interest, 6-11 near misses, 8-12 PEP placements.

These numbers say the skills compute what their contracts and the slice policy say on synthetic
structures. They say nothing about real-world data quality, provider behavior or analyst outcomes;
those are exit-bar items 3, 5 and 7.

### Findings the build surfaced

1. **The connector path could not propose a false match.** The wiring normalizer wrote
   `identifier_conflict: false` for every hit. Fixed, with the schema extension above.
2. **Registry status vocabulary disagreed.** The platform normalizer writes `ACTIVE`; the corpus wrote
   `active`, so a policy written for one failed on the other. The corpus now matches the normalizer, and
   the slice policy uses `ACTIVE`.
3. **The library profiles do not cover the slice.** Five slice skills are in no library profile's
   `allowed_skills`. The generator adds them explicitly (`SLICE_PROFILE_ADDITIONS`); they should move into
   the library's profiles.
4. **Screening completeness covers every visible party.** The library withholds a clear result while any
   entity in the case context (for example, a transaction counterparty) lacks a completed search. The
   evaluator's reference first missed this; the library was right.
5. **The held-out split varies structure, not lists.** Designated and PEP identities are the corpus's fixed
   fictional entries. A held-out set of list entries is open.
