# Azure observability implementation and rollout

Implementation branch · 2026-11-12 · [Architecture and product design](azure-observability-design.md)

Deliver two independently verifiable increments. The first makes Application Insights the Azure trace backend and shows calls to existing Foundry model deployments. The second adds native Foundry Agent Service traces from a real agent invocation. Complete both before describing the integration as end-to-end Foundry agent observability.

## 1. Qualify Foundry and Azure Monitor first

Use [the ehf-test resource group](https://portal.azure.com/#@hariganeshmsn.onmicrosoft.com/resource/subscriptions/2840dd81-b9aa-4345-81b2-ffffc39fd67e/resourceGroups/ehf-test/overview) as the pilot scope. The Azure inventory on 2026-11-12 showed a Central US resource group with one evidence storage account. The pilot therefore starts with new observability and Foundry resources. The evidence account is outside this test.

### Bootstrap the pilot

1. **Plan the minimum resources.** Start with one Log Analytics workspace, one workspace-based Application Insights component for Foundry, and one Foundry account and project with a supported prompt agent and model deployment. Confirm model quota and Agent Service availability for the selected region before applying. Plan scoped ingestion and query identities and the project trace connection. Use short test retention within Azure's supported settings, and review the new resources and expected charges before deployment.
2. **Prove native Foundry tracing first.** Connect the project to its Application Insights component. Invoke a prompt agent with synthetic input and a deterministic read-only tool from a controlled test client. Send a known W3C parent and record the returned response ID. Read the native request and dependency spans under the intended query identity and identify the exact correlation fields. Test content access before using real inputs. This experiment can run before the platform stack is deployed.
3. **Prove the platform integration.** Add a separate workspace-based Application Insights component for platform spans and an internal Collector when the runtime pilot is ready. The two components can use the same test workspace if the content and access checks pass. Apply the Azure reader and verify a platform run trace, the existing Foundry Models call, and the native prompt-agent trace through the normal BFF and waterfall. Use the same resource group for the onboarding and Admin verification exercises.

Capture sanitized fixtures and record the region, agent type, API version, exporter image digest, query context, auth mode and ingestion delay. The backend-neutral reader extraction can start while the Foundry pilot is prepared.

| Experiment | Evidence to capture |
| --- | --- |
| Platform Collector → Application Insights → BFF | Export a known sampled trace with a request, a child dependency and an error. Read it under the deployed query identity with `queryResource`. Confirm exact table names, role and workspace access mode, ID/parent mapping, timestamp precision, status semantics, partial-result behavior and private DNS/egress. Qualify the platform ingestion auth mode used by the target environment. |
| Existing Foundry model call | Run a synthetic request through the current gateway adapter. Confirm the actual inference URL, propagation behavior, provider ID availability and stored safe dimensions. Exercise success, provider failure and cancellation. Confirm which telemetry Azure exposes for this endpoint. |
| Native Foundry prompt agent | Connect the project to an approved Application Insights component. Invoke the configured prompt agent with a deterministic read-only tool. Confirm whether the parent is preserved and which rows carry the response ID when it is not. Repeat with concurrent calls, a tool failure and one early failure. Preserve sanitized fixtures for both verified correlation paths. |
| Foundry content, auth and isolation | Check destination ownership, actual connection, auth mode and allowed log tables. Inspect synthetic content sentinels for prompt, system instruction and tool input/output, including legacy properties. Verify the BFF identity cannot read protected content or an unapproved component. Repeat across two runs and two tenant contexts. |
| Hosted agent follow-up | Repeat the native test for each hosted API surface before enabling it. Verify hosted request attributes, agent identity ingestion permissions, response ID and native span coverage. |

**Decision gate.** Start with prompt agents. If native spans or a deterministic correlation key cannot be verified, ship the platform/Models increment and show Agent Service tracing as unqualified. Record the exact failed capability and retain the Agent Service acceptance gate. If the deployment requires Entra-only ingestion, qualify both the platform and Foundry write paths under that policy before enabling them. A successful BFF query does not prove the writer works.

### Foundry pilot evidence

On 2026-11-12 the `ehf-foundry-trace-pilot` deployment provisioned the `trace-qualification` project in Central US, with a `gpt-5-mini` Data Zone Standard deployment at capacity 1. The project's default `AppInsights` connection targets `ehf-test-foundry-insights`, backed by `ehf-test-trace-logs`. The workspace has a 30-day default retention and a 0.1 GB daily ingestion cap. ARM required model deployment and project creation to run sequentially under the same account. The pilot uses connection-string ingestion for Application Insights and Entra authentication for Foundry API calls.

| Check | Observed result |
| --- | --- |
| Prompt-agent tool loop | `ehf-trace-probe:1` completed two calls on its dedicated Responses API v1 endpoint. The first requested a deterministic local function and the second returned the expected value after the client submitted the function result. The project-wide endpoint rejected the older `agent` request field. |
| Native spans and W3C parents | Trace `3880e868eb4260d06a9a8ee14a3b93ed` appeared within four minutes. Two native `invoke_agent` dependency rows preserved the outbound trace ID and their respective parent span IDs. A `chat` dependency was a child of the second invocation. The local function execution had no separate native tool span. |
| Response ID anchors | Each API response ID matched `gen_ai.response.id` on its native invocation span. The second ID also appeared on the child model span. Resolve by distinct operation IDs and select the matching invocation anchor, since several spans can carry one response ID. This test used a shared trace ID for both requests. The independent-operation case remains part of adapter verification. |
| Query context and normalization | The component-scoped Logs REST API uses `requests` and `dependencies`. The workspace query uses `AppRequests` and `AppDependencies`. Both returned the same three dependency IDs and the same duration values in milliseconds. The component result returned success as the string `True` and the workspace returned a boolean. The query ran under the signed-in operator identity. |
| Sensitive-content routing | All three matching dependency rows contained synthetic content markers in `Properties`. The workspace had zero `AppGenAIContent` rows for this trace. Neither of the documented content-routing feature flags was registered when inspected. Use only synthetic inputs in this pilot. Before production, verify storage policy and prove that the deployed query identity cannot access sensitive content or an unapproved component. |

## 3. Verification and operational behavior

### Connection checks

- Test Collector reachability, BFF query authorization, and actual ingestion separately. Admin verification emits a sampled span and polls for up to ten minutes through the deployed BFF identity. The verification state belongs to the serving BFF process and applied revision. Azure session affinity keeps a browser on that replica during polling. Run the check again after a revision change or replica restart.
- For Agent Service, use a dedicated synthetic invocation and the scoped reader to qualify the policy before apply. Admin displays qualification status and can check current access to the qualified component. Run paid synthetic agent calls during qualification and the canary, which exercises the gateway, receipt, correlation reader, and waterfall together.
- Do not mark an empty OTLP export as end-to-end success. Record sanitized reason codes and correlation IDs on failures. Keep Health refreshes on cached probe results. Bound polling and rate-limit manually triggered verification.

### Regression tests

| Layer | Required coverage |
| --- | --- |
| Reader and authority | Stable span graph, duplicates, cycles, sampling or missing parents, time precision, Azure partial/empty/403/429/timeout responses, limits, no unsafe attributes or free-text labels, verified component scope, zero queries before authorization. Exercise two tenants, run and retry anchors, conflicting operation ownership, and a raw Foundry trace ID submitted directly. |
| Correlation | W3C parent proof, exact response-ID match in the approved project, same conversation across different invocations, separate provider operations, retries, concurrent calls, duplicate response IDs, no-ID failures and one unavailable Foundry source. Preserve native timestamps and links. |
| Deploy and settings | Bicep build/what-if for both Azure paths, idempotent create/reuse, correct resource-scoped RBAC, content policy and no secret material in outputs. Test old profile and receipt compatibility, stale deployment revisions, managed-write rejection, stable probe results across page reload, change log and rollback. |
| End to end | Open an Azure run and Flight Recorder through the normal web entry points as an authorized operator. Verify platform spans, Foundry model call, native prompt-agent spans after D, and partial/late states. Run the existing local Compose trace smoke. With Azure Monitor unreachable, check that runs, receipts and ledger verification continue. |

Publish a deployment runbook for trace delay, Collector queue/backpressure, rate limits, permissions, private DNS, retention and Azure cost alerts. Track sampled trace retrieval, ingestion delay, Collector export failures/drops, Azure query latency and correlated native invocations. Use aggregate dimensions. Pilot in a test environment at full platform sampling with a fixed synthetic workload. Set production sampling and retention after measuring volume, lag, cost and how often a retained platform span has a usable native link.

## 4. Cutover and rollback

1. **Prepare.** Inventory each environment's Collector or Jaeger destination, existing Insights/workspace resources, Foundry projects, networking, IAM and retention. Save the applied deployment revision and identify where to read pre-cutover traces. Use the review to resolve destination ownership, auth and Foundry content policy.
2. **Deploy the reader and destinations.** Apply the new infrastructure and deploy the BFF with the Azure reader available. Keep the current reader active while the new path passes synthetic verification. Validate Azure under both the bootstrap and runtime network paths when they differ.
3. **Canary and switch.** Start in test, then one Azure environment. For an existing Jaeger deployment, use a short reviewed Collector fan-out if needed to compare new traces, or use separate synthetic canaries where fan-out would expand access or cost. Apply the Azure reader and Collector destination under the same reviewed deployment revision. Persist the cutover boundary and route historical traces through the approved previous binding during its retention window. Qualify Foundry model tracing and enable Agent Service per project after its independent gate.
4. **Observe and retire.** Compare synthetic and representative run traces before expanding. Alert on ingest/query failure and correlation loss. Remove the Azure Jaeger image and infrastructure after migration has passed the agreed rollback and retention window. Legacy in-memory traces can expire or disappear with a Jaeger restart. Keep normal run and audit navigation available.
5. **Rollback.** Reapply the previous reviewed deployment revision and previous destination/reader routing. Keep data already written to Azure and retain its time-bounded read binding when policy permits. If only a Foundry source fails, disable that binding and leave platform Azure tracing active. Repeat the synthetic checks after rollback. Preserve resources and role assignments needed by any still-active or historical binding.

The implementation is ready for Azure production when the deployed identities pass end-to-end export and read checks, tenant and content isolation tests pass, managed configuration changes and rollback are exercised, and the qualified Foundry prompt agent shows native correlated spans in the run trace. Hosted-agent coverage is reported for each separately qualified API surface.
