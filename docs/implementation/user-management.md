# Platform users and roles

The Platform console includes **Users & roles** at `/platform/users`. Administrators search Microsoft Entra ID by name or email, select a person, and assign multiple built-in human roles. Their name, email and identity are populated from the directory; no subject ID entry is required. Search marks existing workspace users, disabled accounts and missing email addresses as unavailable for selection. Auditors can inspect workspace users and role permissions but cannot search the external directory or change access. Account creation and invitations remain with the identity provider.

Directory search automatically uses a tenant-specific Entra `OIDC_ISSUER` (`https://login.microsoftonline.com/<tenant-guid>/v2.0`), `OIDC_AUDIENCE` (the app client ID), and the server-only `BFF_OIDC_CLIENT_SECRET`. The Azure `deploy:azure:foundation identity` command and automatic OIDC resource recipe declare and consent to Microsoft Graph **User.Read.All application permission** on this app. Rerun the identity step for an existing deployment; it retains other API permissions and skips existing grants. The deploying operator must have directory application-management and consent authority. Existing/manual resource verification checks consent without changing the app. For other deployment paths, grant this permission and administrator consent in Entra. For a separate directory-reader app in the same tenant, set `IDENTITY_DIRECTORY_CLIENT_ID` and `IDENTITY_DIRECTORY_CLIENT_SECRET_REF` (`env:NAME` or `file:/run/secrets/name`). No Graph credential or token reaches the browser. Leave **User assignment required** disabled on the sign-in enterprise app: the platform directory applies saved roles after authentication. Automatic creation reconciles this setting on its owned app. The existing environment setup configures the sign-in app; the add-user screen links to setup when no supported connection is configured. Other OIDC providers continue to support sign-in; their directory-search adapters are not implemented yet.

Graph requests use the fixed Microsoft Graph v1.0 origin, bounded prefix searches over display name, mail and principal name, and a maximum of 25 results. Administrators can refine the search when more results exist. Import re-fetches the selected user from Graph, rejects disabled/missing-email accounts and never trusts profile fields from the browser: the creation contract accepts only the directory user ID, roles and change reason. Provider failures, missing consent and throttling have separate UI messages. See [Microsoft Graph list users](https://learn.microsoft.com/en-us/graph/api/user-list?view=graph-rest-1.0) and [client credentials](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-client-creds-grant-flow).

Apply migration `057_platform_users.sql` and the control database grant matrix before starting the updated BFF. The directory and its access audit are tenant scoped with forced row-level security. Only control-api can change the directory. Each change records the actor, reason and before/after values in the same transaction; revisions reject stale edits. The service rejects workload roles, duplicate subjects/emails, removal of the last managed administrator and removal of the caller's own administrator role.

The standard BFF resolver looks up each verified human subject through the private, authenticated-edge endpoint `/v1/identity/access` on every request, including existing sessions. Entra imports store `entra:<tenant-id>:<object-id>` as their internal identity. Verified Entra token `tid` and `oid` claims produce the same directory identity; the app-specific `sub` stays the actor ID for existing records and audit continuity. Directory lookup checks the stable identity first, then the original subject for older manually entered users. Names and emails never establish authorization. Self-administration and transaction-time actor checks also recognize the verified directory identity. See [Entra token claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference).

A managed user's saved roles replace the provider's role claims; permissions combine across those saved roles. Subjects without a directory entry retain their provider-managed role assignments, allowing existing deployments and the first administrator to keep access. Directory failures fail closed. Custom injected principal resolvers own access resolution and can opt into `directoryAccess` through `resolveUserAccess`. Migration 057 stores both provider identities and role assignments.

The UI uses contract-generated operations `getAdminUsers`, `getAdminRoles`, `getAdminIdentityProvider`, `getAdminIdentityProviderUsers`, `postAdminUsers` and `putAdminUsersUserId`. Workspace/configuration reads require `admin.read`; directory search requires `admin.write`. Changes also require session CSRF and an origin check. `Platform.Admin` and `Platform.Auditor` retain their existing action definitions. Roles and their permissions come from the server.

UI journeys run with `pnpm --filter @ehf/e2e-ui e2e plt-users.spec.ts`. Database integration checks use a dedicated disposable PostgreSQL database via `EHF_USERS_TEST_DATABASE_URL` and run `packages/persistence/src/users.test.ts`; the test creates the directory tables if absent and a temporary non-superuser login to exercise tenant isolation.
