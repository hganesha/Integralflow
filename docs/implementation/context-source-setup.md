# Context source setup

Status: structured-source implementation, 2026-11-09. This implements the initial connection/mapping/sample workflow from [context-experience.md](context-experience.md) and provides case preview and qualified gateway acquisition. Scheduled snapshot refresh/checkpoints, mapping extensions, filtered lexical document retrieval and versioned platform Application/holding contracts are described in [context-operations.md](context-operations.md).

The existing [Enterprise context sources](context-source-connectors.md) workflow remains available at the platform Context sources surface and `/v1/context-sources`. This Contextboard workbench uses `/v1/context/*`, the `@ehf/contracts/context-setup` contracts and separate revision/qualification tables. Existing enterprise source bindings are not migrated or enabled implicitly.

## User flow

Open Context → Edit context, the Context catalog's “Edit context · Connections and mappings” link, or `/context/connections?product=party360&agent=...`. Existing `/context`, product/agent/mode/draft selections and preview links remain available. `/context/sources/:sourceId` and `/context/mappings/:mappingId` open the same workbench.

Platform → Data connectors (`/platform/data-connectors`) provides Status, Calls, and Refresh history. Status reads the shared source definitions, schema pins, selected mapping enablement, and available gateway adapter credential states. Calls shows context acquisition receipts (`context.records.fetch.v1`) with decisions, provider results, latency, and run links; pagination scans gateway receipt pages rather than claiming an all-time source-call total. Refresh history shows scheduled batches, quarantine errors, committed checkpoints, and runs. These views require `draft.read`; call receipts additionally require `receipt.read`, and adapter status requires `capability.read`. Configuration links return to Context editing. Mock mode has no configured sources or live qualification.

1. Choose an existing shared connection, or save an administrator-authorized PostgreSQL connection referencing an operator-mounted credential.
2. Select the approved table/view, source columns, subject key and observation column. Save a source revision. Discover and pin its live schema before a live sample.
3. Create the Entity/Party mapping or add canonical objects from the pinned ontology. Visual controls and JSON code mode edit one declarative expression representation. Connection-scoped stable IDs, field reads, literals, trim/case conversion, decimal/time parsing, arrays/objects and approved enum lookups execute on the server. Unsupported complex visual rules remain visible and retained in code.
4. Save the mapping revision. Upload a JSON sample file, choose a fixture, or request a bounded live sample. Source data and field lineage are returned in a protected expiring report; rejected related rows are not partly emitted.
5. Repair issues and save a new revision, then rerun. Optional consumer assessment checks fields/counts per subject against task requirements and the agent ceiling. It explicitly leaves policy, dynamic freshness, predecessor parameters and runtime authority for a case preview.
6. Preview a case using its admitted plan, an explicit matching task node and, when required, its approved source-context digest. Enablement accepts only the exact eligible live-tested revision and an executable released plan. Uploaded or fixture reports cannot enable live acquisition.

Play's existing field-ceiling calculation is labeled Access coverage. Source inventory, sample qualification, source observation and case/task availability are independent facts. The source workbench reports actual gateway adapter enablement separately from implemented discovery/sample support.

## Service and storage boundaries

`packages/contracts/src/context-setup.ts` defines the typed source configuration and mapping representation. The isolated request schema bundle is generated by `export_context_contracts.mts`; `ui-sync` regenerates/checks it. This keeps recursive mapping expressions out of the legacy flat contract exporter.

`packages/context-mapping` compiles and executes bounded deterministic mappings using `@ehf/library-contracts`. It emits candidate records and lineage, never authoritative tenant/case/provenance envelopes or case writes. Required canonical fields and closed data schemas come from the vendored ontology and lock. Unknown enum values, absent identities, conflicting keys and unresolved sample relationships are retained as issues. Row counts, record counts and duplicate counts have separate denominators.

`packages/context-postgres` provides shared read-only native transport for setup and the gateway. Source identifiers are validated and quoted; subject values are bound parameters. It enforces approved resources, at most 20 requested subjects/100 rows, connection/query/lock deadlines and a 512 KB result budget. A limit-plus-one read reports truncation. Discovery fingerprints the permitted columns' types and nullability. Source credentials must independently restrict database access; the service also runs reads in a read-only transaction.

`apps/control-api/src/context-setup-routes.ts` owns configuration, discovery, mapping compilation, sample execution, consumer assessment, source-use preview proofs and enablement. Live reads use the existing approved source-policy artifacts and evaluator, with no normal runtime run created for sampling. Samples persist separately from case data in `harness_control.context_samples`. Configuration revisions are immutable. Migration `047_context_setup.sql` forces tenant RLS, and the grant matrix gives the gateway read access only to the definitions/enablements it executes.

The BFF's context module derives product/access views from integrity-checked canonical catalog artifacts. Read-only catalog verification is separate from executable skill registration; successful catalog display does not qualify a skill or source. Sessions, CSRF, verified identity forwarding and upstream response validation apply to the new routes. Mock source inventory is empty; mutations explicitly require the real service rather than manufacturing live qualification.

Sample content is available until its server-set expiry, only within its tenant and to its creator or an authorized release approver. Reading a live report rechecks current source authority. Reports are not runtime packs. Expired reports return 404; deployments must arrange tenant-scoped deletion of expired sample rows under their retention policy. Enablement retains the report digest even after payload expiry.

## Case preview

`POST /v2/cases/:caseId/context:preview` accepts an admitted plan and node under interactive `case.read` and `draft.read` authority. The plan must match the case's pinned digest. The case service performs target-selector projection and classification treatment before preparing the context; the BFF does not fetch an unrestricted snapshot and reconstruct a packet.

Hosted skills and preview share `prepareSkillContext` for pack assembly, policy resolution, parameter binding and structured skill-input admission. Models use the existing assembler and prompt renderer. Preview renders the actual pack, model view, structured skill input when available, gaps and exclusions. It never invokes a model/skill, starts a runtime run, records/promotes a runtime pack, or mutates a case.

For source-backed sections, the case service issues a metadata-only challenge. The control service rechecks historical source references against current approved source/access/policy artifacts and signs a separate proof. Its audience is `ehf-case-preview`; it binds tenant, actor, plan, node, exact projected snapshot and source decision IDs for at most 30 seconds. It cannot authorize a runtime invocation or case write. The case service holds the challenged snapshot in a bounded short-lived cache so observation-time changes cannot cause the proof to authorize different data.

Set `CONTEXT_PREVIEW_PRIVATE_KEY_PEM` on the control service and `CONTEXT_PREVIEW_PUBLIC_KEY_PEM` on the case service. For local development only, both can use the same `CONTEXT_PREVIEW_SECRET` (at least 24 characters). Source-free preview does not need a source-use proof. Pre-case samples remain candidates; this implementation does not disguise them as committed case snapshots.

The context plane also supports explicit `node.config.requirePerSubjectContext: true` for record-reading nodes. With that opt-in, a subject's record minimum is checked independently; another subject's records cannot satisfy it. Existing plans retain their original aggregate requirement semantics.

## Enablement and runtime acquisition

`POST /v1/context/mappings/:id/enable` requires `release.activate`. It checks the report, exact mapping/compiler/schema/catalog/resource/connection pins, current credential generation, fresh discovery, approved source authority and executable release. Configuration advisory locks and artifact/release row locks close the relevant check/activate races. A failed test or incomplete mapping does not overwrite an earlier enabled revision.

Enable the gateway module explicitly with `GATEWAY_ADAPTERS=default,context-postgres`. The connector ID is `context-postgres:<mappingId>` and the capability is `context.records.fetch.v1` with effect `read`. Register and qualify the concrete connector through the existing gateway/source-policy governance. A saved connection or successful discovery does not change its operational state to `live_ready`.

The admitted source binding's `mappingVersion` must equal the compilation digest. Its datasets/fields must cover the exact resource. PostgreSQL network coordinates are credential-free `postgresql://host:port/database` entries in approved endpoints. Local transport is limited to loopback. The operator-mounted DSN is checked against those approved coordinates before connection.

An acquisition node's input is `{ "subjects": ["source-customer-key"] }`, with up to 20 source keys. Its released plan supplies the actual authorization and a case-write declaration such as `RecordCanonicalRecords` using `output.records`; enabling alone does not ingest into arbitrary cases. The gateway loads the enabled mapping, rechecks its current pins and source policy, executes the same mapping plan and returns canonical records with gateway invocation/source-use provenance. An acquisition derives record version IDs from the candidate version, mapping and gateway invocation, so retries of one invocation replay identically while a new receipt cannot conflict under the same immutable version. Invalid, ambiguous or truncated batches fail before case commit. The existing authorized case command path provides immutable versions, idempotency and supersession.

Mount the selected credential reference in both control and gateway environments. Example configuration (values supplied by the operator; never entered into the browser):

```json
{
  "tenantId": "tenant_example",
  "connectorId": "context-postgres:customer-party",
  "generation": "v1",
  "connectionString": "<operator-managed PostgreSQL connection string>"
}
```

Store that JSON under a reference such as `CONTEXT_SOURCE_CUSTOMERS`. Rotate its generation whenever credentials or identity scope change and save/requalify the connection/resource/mapping chain. Connection configuration needs both draft authoring and `integration.connector.write`; enablement and pause remain separate operator authorities.

## Verification and remaining work

The HTTP Playwright journey in `e2e/ui/context-http.spec.ts` creates a source/mapping, rejects a row, repairs its enum visually, round-trips code mode, saves a new revision and reruns. It checks accessibility and that uploaded samples cannot enable live use. Run it against a migrated HTTP stack with `CONTEXT_HTTP_URL` and matching `WEB_E2E_PORT`; the ordinary mock suite skips this test.

Focused tests cover deterministic mapping/lineage, schema/identity errors, bounded PostgreSQL reads, tenant/revision isolation, source destination/credential scope, protected sample reports, preview projection/no writes and proof scope. Existing runtime suites exercise the shared preparation change. Live enterprise qualification still requires actual mounted credentials, approved source artifacts and a released plan; local test data is not qualification evidence.

Remaining plan extensions: asynchronous/cancelable sample jobs, richer source discovery, draft autosave/session recovery, staged-sample runtime-equivalent previews, subscription/ceiling authoring beyond Tune, CDC/paged incremental ingestion, source-backed document-use delegation, semantic/hybrid retrieval, and Application library consumer/product releases. See context-operations.md for implemented refresh, mapping, search and platform contract boundaries.

## Vendor API case sources

Salesforce/FSC and Fenergo API resources now use the same connection/resource/mapping/sample/enablement workflow. The [implementation and qualification guide](context-api-connectors.md) covers mounted OAuth credentials, schema discovery, the released acquisition plan, reviewed case subject bindings and explicit Pull context actions. API pulls commit immutable canonical records before they become available to case/task context. Source setup and case preview remain separate; preview makes no vendor call or case write.

The current ontology and declared relationship catalogue remain authoritative. Unsupported external workflow and incomplete assessment details stay source evidence. API sources have no CDC, notification polling or scheduled refresh; PostgreSQL snapshot scheduling remains independent. Bank-specific schemas and mapping profiles require actual tenant qualification. The [v2 plan](context-connectors-v2-plan.md) records the portfolio and later delivery gates.
